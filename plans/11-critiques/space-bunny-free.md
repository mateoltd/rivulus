# Critical review: plans/11-node-compat-pivot.md

Read only the plan. I did not verify any claim it makes about repo state (`bench/compare.py` bands, `bench/djs-equiv` skeleton, core transport injection, MIGRATION.md hit counts), so claims below are marked either *plan-internal* (provable from the text) or *unverifiable-from-plan*.

## 1. API boundary (section 3) and milestone sequence (section 6)

**Wrong, not missing:**

1. **Two contradictory handle models.** 2.2 mandates "No `External` values escape without an explicit `close`/`dispose`", but 3 defines the handle as "an opaque handle (numeric id, never the token)". A numeric id is not a napi `External`, so 2.2's `External` clause is vacuous under 3's design. More importantly the id design throws away napi's handle model and reinvents a global id-to-client registry, which then needs: forgeable ids (arbitrary numbers must produce a typed error, and 3's error list has no "unknown handle" member), id recycling/wrap policy, a `WeakMap`-free global that leaks if `close` is forgotten, and event routing that carries the raw id back through the threadsafe function, which re-opens the cross-wiring hole. Use a `#[napi]` class instance with a finalizer plus a JS-visible `dispose()`; the `.d.ts` can still present it as opaque.
2. **M2 is impossible as ordered.** 2.2 and M2 both say the `.d.ts` is *generated* and checked in, but napi generates types from `#[napi]` items, and the section-3 functions do not exist until M3. M2 before M3 produces an almost-empty `.d.ts` and a fixture test asserting nothing. M2 must be merged into M3 or moved after it.
3. **M2's fixture test is circular.** "fixture test asserting the documented surface exists with the documented names" is meaningless if the expectation source is the generated `.d.ts`. 2.2 says the `.d.ts` is "checked in and diffed in CI" but never says diffed against what. You need a hand-written contract file (name, arity, sync-vs-async, return shape) and a diff of generated output against it. As written the guard cannot fail.
4. **`streamPages` is the single worst boundary choice in the plan** and directly contradicts 2.2. 3 offers "plain arrays/iterables". A Rust-backed JS `AsyncIterator` cannot pump itself without a threadsafe function, so JS may hold a live Rust allocation for an unbounded time (2.2's "no retained graphs, every read is a droppable snapshot" is false for iterators), and a sync iterator means one `Promise`/object allocation per `next()` per message, the worst case for the headline metric. Also unconsumed iterators leak a Rust allocation for process lifetime, and 2.4's "narrow the boundary" response does not apply. Pick one: return a coarse `AsyncIterable<Page>` of pre-shaped batches, or drop `streamPages` from the binding.
5. **Sync vs async is unspecified, and it decides the GC numbers.** Section 3 never says which functions return Promises. `getHealth`/`getLatencies`/`getUptimeMs`/`getCacheStats` are trivially synchronous; a Promise per call is pure V8 garbage for no benefit. This is a headline-metric decision being left implicit while M2/M3 freeze types around it.
6. **The error contract is underspecified in a way that blocks M2.** 3 says `login` "rejects with the typed error string" and `close` "rejects further calls with `shard down`-family strings". A napi Promise cannot be rejected with a bare string; you reject with an `Error` whose `.message` (or `.code`) carries the string. Which one, and what `close`'s rejection is if `close` is sync-then-invalidate, must be pinned before types are generated, not asserted in M5.
7. **String-only `verifyWebhook` cannot be byte-exact.** 3 claims "same concat rule (`timestamp_bytes || body_bytes`)" parity with `interactions::verify`, but `body` crosses as a JS string: napi converts UTF-16 to UTF-8, so a non-UTF-8 interaction body cannot round-trip, and the "pure, no I/O" framing hides that. Needs a `Buffer`/`Uint8Array` path to match Rust's `&[u8]`.
8. **"rejects with the typed error string" vs "numbers/strings only" contradictions.** `getLatencies` is plural but section 3 says the getters return "numbers/strings only"; that is an object or array, and it will surface as a `.d.ts` mismatch in M2.
9. **`close` lifecycle is unspecified where it matters.** Is `close` async (it must drain/release the threadsafe function)? What happens to an in-flight `login` promise during `close`: reject or hang? A hang is worse than a wrong value in a gateway client. There is no `closeAll`/process-exit cleanup, and no statement that `close` is mandatory for a clean exit.
10. **`createClient` option shapes are unspecified.** `intents` (number vs discord.js bitfield), `cache` (which values?), `sharding` (there are no shard helpers, so what does `sharding: true` do?) are all undefined. 3's parity claims ("matches `Client::login` semantics exactly", "same clamp rules as Rust") have no referent. Also the token plainly exists in the V8 heap from `createClient` onward, which 2.1 ("hot state lives in Rust memory, never in the V8 heap") papers over; it will also appear in M4's heap snapshots. Trivial, but say it.
11. **1.5's gate set has no JS/TS gate.** No `tsc --noEmit` over the checked-in `.d.ts` plus a `.ts` fixture, no lint, no `npm test` in the standard evidence list. A repo whose deliverable is a checked-in generated `.d.ts` with zero type-check is under-gated.
12. **Two milestones both claim the Node CI job.** M5 is "mock-first boundary suite in CI (Node job, no token)"; M7 is "node CI job (20 + 24)". Sequence is contradictory, and until the Node job exists no M1-M6 milestone is actually gated by Node.
13. **M7 violates 1.5** ("one milestone per turn"): README, MIGRATION row, hygiene re-check, `npm pack`, the node CI job, and the deny note in one turn.
14. **M4 can invalidate M2 and M3, and the plan says "written once here, measured there" (M3) while 2.4 promises to change the surface if the binding loses.** There is no rollback path for the types, the fixture test, or the example consumer, and no stop condition anywhere in the plan except 4's "if no 2.x qualifies, stop". Add per-milestone abort criteria and an explicit statement that M4's failure is a legitimate pivot-or-stop outcome, not a refactor mandate.

**Node 22 omission (4) I think is wrong, not merely a choice:** "20 is engines floor, 24 is local truth" drops the LTS line most production users run while covering near-EOL 20 and odd/current 24. Either test 20/22/24 or raise `engines` to `>=22`.

**M0 (6) I disagree with on position:** a mass deletion across 10+ files plus 39 MIGRATION.md hits, with a taste-based judgement ("no value to the reader") and no gate that actually tests judgement, lands as a large unreviewed diff *before* the substantive work, so any core regression is ambiguous between the two. 1.1 only binds new content, so M0 is not a prerequisite for anything. Drop it or split it.

## 2. Does the GC-reduction story hold?

**No, and the core of the failure is a category error: the plan reasons about survivors and calls it GC pressure.**

15. **The measurement and the headline are misaligned.** GC pressure is allocation *rate* plus survivors. 2.2/2.3 argue only about retention ("snapshot the caller can drop", "retain nothing", "no per-message object graphs are retained"). 5.2's primary gate is "heap after forced GC", which measures survivors only. A design that allocates two V8 objects per event and drops them immediately looks perfect on that metric while being strictly worse than discord.js on actual GC work. The negative control (5.2(c), "binding with consumer retaining everything, must measure worse") is exactly the case that distinguishes the two theories: under an allocation-rate metric with retain-then-drop-in-the-same-tick, (c) need not measure worse, and the plan's own gate would break. The claim "if the binding allocates more per event than the discord.js baseline the milestone fails" (2.4) is therefore not what 5.2 measures.
16. **The decisive control is missing: discord.js with its cache disabled.** The headline win in (a) vs (b) comes almost entirely from 2.3's consumer choice (no per-message cache) versus discord.js's default cache, not from napi. If discord.js-with-cache-off beats the binding on the identical mock workload, 2.4's "narrow the boundary" response does not save the experiment, because the remaining cost is the per-event V8 materialization that no snapshotting removes. Add that arm, or the comparison is not a claim about the binding.
17. **JSON-string events are the wrong shape and 2.2's justification is wrong.** "Events cross as serialized JSON strings through a threadsafe function" materializes every event twice: a Rust `String`, then a full V8 parse into objects in the callback, then the consumer's own object. A hand-built napi object, or a pre-shaped columnar array payload, allocates less. Worse, 2.2's "No per-message object graphs are retained on either side" is a retention claim used to justify an *allocation* decision; it does not address the cost paid. Also "batched per tick" is left undefined (what is a tick, what is the cap, what happens on overflow) while 7 defers batching policy to M4, even though 2.4 names batching as the primary lever.
18. **No falsifiable hypothesis.** There is no predicted bytes-per-message or objects-per-message budget anywhere. 2.1's "cheap to point at" is about Rust. On the JS side the floor is real and unstated: snowflakes correctly cross as strings (u64 does not fit in a double), so every event spends multiple short-lived V8 string allocations. State the predicted per-event V8 allocation floor so M4 has something to refute.
19. **2.1's evidence list is partly category-confused.** "`AtomicU64` request ids" never enter the V8 heap and cannot be GC pressure; `Box<str>` addresses Rust fragmentation. Fine as Rust work, but it weakens 0's claim that "every layer choice below states how it serves" the GC goal.
20. **2.2's type-drift rationale is wrong.** "Checked in and diffed in CI so type drift fails loudly instead of silently allocating new shapes at runtime": types are erased, so a drifted `.d.ts` cannot allocate anything at runtime. The real value of the check is catching a public API break at the npm boundary. Keep the guard, fix the reason.
21. **RSS is the wrong third metric and invites the wrong conclusion.** The binding's real memory risk under burst is Rust-side (see 22), and V8 heap can shrink while Rust grows. RSS will move for allocator and arena reasons unrelated to either hypothesis.

## 3. Node/napi boundary risks

22. **Unbounded Rust-side queue growth is invisible to M4.** A napi `ThreadsafeFunction` has a fixed queue; when full, `napi_call_threadsafe_function` returns a status (`QueueFull`/`Closed`) that the plan never mentions, and the usual fallbacks (block, or drop) are undecided. If the binding batches into a Rust channel that grows without limit under burst, 7's "backpressure under burst dispatch" is not merely a batching-policy question: it is an unbounded Rust allocation that RSS is the only listed metric able to catch, and RSS is buried in a three-metric list whose primary gate is V8 heap. This is a leak that the plan's own headline measurement cannot see, and 7 defers it to M4.
23. **Nothing about the event loop staying alive.** A live threadsafe function keeps the Node event loop referenced; without `unref` plus an explicit release, `npm run smoke` (M1) and every Node test (M5) hang at exit instead of exiting 0. This is a certain, cheap-to-hit failure and it is not in 7.
24. **Handle lifecycle against napi's actual model.** 3's numeric-id registry sidesteps `External`/class-instance finalization and reintroduces the manual-lifetime bug class that napi's `Finalize`/`dispose` already solves. 2.2 says "leaked handles fail M5 tests" but names no mechanism (a live-handle counter asserted zero at process exit, or a forced-GC-and-check pass). Without one, the rule is unenforceable.
25. **Generator version pinning is unaddressed.** 7 pins the JS tree via `package-lock.json`, which does not pin the `napi` CLI. Regenerating bindings on a machine with a different `napi` CLI version rewrites the checked-in `index.js`/`.d.ts`, and 2.2's "diffed in CI" then fails for reasons unrelated to the API. Pin the CLI exactly and document the regeneration command.
26. **No prebuild/ABI story.** 4 targets Node 20 and 24 (ABI 115 and 137). Without prebuilds, every consumer needs a Rust toolchain, and 7's "Node version drift" risk is the smaller of the two. `npm pack` (M7) with no prebuild plan is not shippable.
27. **"If no 2.x qualifies, stop and report" is the only stop condition in the plan**, yet the status line calls sections binding on landing. 4 defers the napi version, 2.4 defers the boundary shape, 7 defers batching and deny coverage. 0/6's "binding once this plan lands" is not true of the plan as written; say what is provisional.
28. **Supply-chain asymmetry, and I think 4 has the default backwards.** 4 permits "a documented gap with a reason, never silence" for `node/`'s deny pass, deferred to M7. `node/` is the crate that ships the binary, i.e. the highest-value dependency surface in the repo, and it is the one excluded from the workspace `all-features` graph. The out-of-policy exception belongs on the *workspace* test crate, not the shipped one; close this in M1.
29. **`node/` outside the workspace silently escapes 1.5's gates.** `cargo fmt --check` and `cargo clippy --workspace -D warnings` cover nothing in `node/`, for the whole plan. Worse, `node/` resolves `../crates/rivulus` with its own feature set: if napi needs extra features there, the shipped binary runs a differently-configured core than the one CI tests, which contradicts 2.1's "unchanged semantics". Add explicit `fmt`/`clippy`/`test` commands scoped to `node/` to 1.5, plus a feature-parity assertion between the workspace build and the `node/` build.

## 4. Test methodology (section 5, and 1.4)

30. **5.1's "in-process" is the largest unestimated risk in the plan and is missing from 7.** A napi addon with a background Rust thread doing real gateway work cannot be handed a mock "in-process" unless the core already exposes injectable gateway and REST transports. If it does not, M5 requires core refactoring on the critical path (unplanned, unsized) and the mock must become a real socket server. If it does, the plan should say so and name the seam, because 1.4's mock-first premise depends on it.
31. **The discord.js arm needs a protocol-correct socket server.** 5.2(b) runs `bench/djs-equiv` "against the same mocks". A mock the Rust core can accept in-process cannot serve discord.js, whose gateway manager and REST handler require a real `ws` handshake, real HTTP, real rate-limit and 429 handling. Building a sufficiently faithful mock gateway is a sub-project with no milestone, and its fidelity determines the headline number.
32. **M4 has no parameters.** "N guilds, M messages" are placeholders. The GC claim is scale-dependent (per-message cost, cache growth) and a band is meaningless without fixed, published N, M, message size distribution, warmup, and repeat count. Reproducibility is not achievable as written.
33. **"warn-only first landing, gate after one clean nightly" is not a gate.** One sample from the flakiest run in the pipeline (machine load, GC heuristics, V8 version drift between local v24.21.0 and the nightly image) is not evidence for a distribution-valued metric. Require N runs, report the median and dispersion, and set the numeric band in advance. Also `"same style as bench/compare.py"` is an unverified appeal to an external file that may not define GC bands at all; define the numbers in this plan.
34. **Heap-snapshot object counting is the wrong instrument.** It is noisy, parse-brittle, and a maintenance tax. Report allocated-bytes-per-message and scavenge count / GC pause totals from `--trace-gc`, plus a survivor count from post-GC heap as a secondary. Keep RSS only as a leak tripwire, for the Rust-side reason in 22.
35. **Live validation comes after the surface is fixed and gated.** M6 sits after M5, so no real gateway is ever touched until the boundary, the `.d.ts`, and the gate are locked. For a protocol-heavy client, mock fidelity is where the bugs are, and a hand-written scripted gateway encodes the plan author's model of the protocol rather than Discord's. Move one read-only live login + `fetchPage` to before M3.
36. **The live harness structurally cannot validate the headline.** 1.4's fixture is 1 guild, 4 channels, **0 messages**, and the nightly djs compare is blocked below 100 guilds. So M6 proves login works and `fetchPage` returns empty; it validates no snapshot shape, no ordering, no clamp, and certainly no GC claim. M6 should say outright that it is a connectivity check, not surface validation, rather than being presented as validation.
37. **1.4 vs 1.5/5.3 tension.** 1.4 says "Mock-first always for Discord-dependent tests"; M6 is a Discord-dependent, non-mock test. Reconcile the text, since 1.x is declared non-negotiable.
38. **Token-leak testing only covers logs, not the error path.** 5.1 greps captured output for the mock secret. 1.5 greps the repo before commits. Neither covers an *error message* that embeds a URL carrying a token, or a heap snapshot containing the token created at `createClient` (see 10). Add a redaction assertion on the failure path, not just the happy path.
39. **Live evidence has no artifact rule.** 5.3 produces redacted console output; 1.5 demands "evidence". Nothing requires committing a redacted evidence file, so M6 becomes a claim in a chat log rather than a diffable artifact, and the next turn has nothing to compare against.

## Bottom line

The pivot is worth doing, but as written the plan (a) picks a handle model that contradicts its own GC rules, (b) orders type generation before the code that generates it, (c) offers an iterator API that violates its own boundary rules and is the worst possible choice for its headline metric, (d) measures survivors while claiming to reduce GC pressure, and compares against a baseline that wins on consumer configuration rather than on the binding, (e) omits the two controls that would actually decide the experiment (djs-with-cache-off, allocation rate), and (f) does not state the core-injection seam that mock-first depends on, or any stop condition beyond the napi version. Fix 2, 4, 5, 16, 17, 30, and 31 before M1; the rest can land as written revisions during the milestones.
